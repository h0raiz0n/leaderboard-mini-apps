## 1. Честный технический диагноз: почему бот лагал 10+ секунд и спамил

### Корневая причина №1: Природа Google Apps Script (Cold Starts & HTTP Chaining)
* **Как было настроено:** дилер жмёт кнопку в Telegram $\rightarrow$ Telegram шлёт Webhook в Google Apps Script (`doPost`) $\rightarrow$ Apps Script «просыпается» от холодного старта (3–5 сек) $\rightarrow$ делает синхронный запрос `UrlFetchApp` в Firebase (1–2 сек) $\rightarrow$ делает синхронный запрос `UrlFetchApp` в Telegram (`editMessageText` / `sendMessage`, 1–2 сек) $\rightarrow$ возвращает `200 OK` в Telegram.
* **Итоговое время отклика:** **6–10+ секунд на один клик!**

### Корневая причина №2: Webhook Storm (Шторм повторных запросов Telegram)
* Telegram ожидает HTTP 200 в течение 3–5 секунд. Если Apps Script не успел ответить из-за холодного старта, Telegram считает запрос упавшим и **начинает циклично повторять его каждую минуту**.
* В результате при нескольких нажатиях `/start` сервер Apps Script захлебнулся в очереди одинаковых вебхуков, что привело к цикличному спаму и зависанию кнопок выбора структуры.

### Архитектурное решение проблемы:
1. **Для мгновенного отклика (Instant UX < 50ms):**
   * Основной боевой пульт дилера должен работать через **Telegram WebApp / Mini App**, который напрямую на клиенте смартфона общается с Firebase через сокет/REST ($<30$ мс) без тяжелых промежуточных запросов через Apps Script.
   * Чат-бот Telegram используется как точка входа, авторизации и уведомлений, с мгновенным ответом `200 OK` до выполнения тяжелых фоновых операций.

## 3. Протокол работы исполнителя (Execution Rules)

1. **Строго по очереди:** Брать ровно одну задачу `[ ] TASK-...`, реализовывать её, затем брать парную задачу `[ ] VERIFY-...`.
2. **Обязательная проверка в браузере/консоли:** Запуск тестов, проверка отклика и отсутствие регрессий.
3. **Чистый Git:** Каждый завершенный шаг фиксируется коммитом, деплоится в Apps Script / хостинг.
4. **Обновление статуса:** В файле `ORCHESTRATOR.md` задача отмечается как `[x]`.
